# FC2_W3 Epilogue: CUTLASS Clone Plan

## Root Cause (SASS-verified 2026-04-03)

CUTLASS epilogue per sub-iter pipeline:
```
[Pre-unpack source BF16→FP32 via SHF+LOP3 — hides in TMEM latency]
LDTM.16dp256bit.x8 → 8 FP32 acc values
FFMA ×32: alpha * acc + source_fp32     (long FP32 compute chain)
SHF+LOP3+PRMT: FP32→BF16 conversion    (manual byte manipulation, NOT F2FP)
HFMA2 ×8: result * 1.0 + bias_bf16     (BF16 bias add)
STS.128 ×8: interleaved with HFMA2+PRMT groups
@!PT LDS RZ ×4: pipeline drain fences
MEMBAR.ALL.CTA + FENCE.VIEW.ASYNC.S + BAR.SYNC.DEFER_BLOCKING
```

Chain depth per output group: FFMA → SHF → LOP3 → PRMT → HFMA2 → STS = **5 serial deps**.
This forces ptxas to pipeline group N+1's compute while group N's STS is in-flight.
Result: 8-12 compute ops between each STS pair.

Our epilogue per sub-iter:
```
LDTM.x32 → 32 FP32 acc values
16× F2FP (all independent) → 16× HFMA2 (all independent) → 16× HADD2 (all independent)
4× STS.128 clustered (2 ops between #1→#2, 0 between #2→#3→#4)
[no @!PT LDS fences]
MEMBAR.ALL.CTA + FENCE.VIEW.ASYNC.S + BAR.SYNC.DEFER_BLOCKING
```

Chain depth: F2FP → HFMA2 → HADD2 = **3 deep, but all groups independent**.
ptxas batches all compute then all STS. Only 2 ops shadow between STS pairs.

- [x] 2 barriers per sub-iter (post-STS + post-TMA-store)

## Phase 1: FP32 epilogue + @!PT LDS fences + pre-unpack — DONE, FAILED

**Implemented**: `-DCUTLASS_EPILOGUE` flag in `fc2_w3.cu`.
**SASS result**: ptxas defeats BOTH source-level changes.

### 1a-1c: FP32 pipeline (FADD → F2FP → HADD2 → STS) — FAILED
- [x] Pre-unpack residual BF16→FP32 before TMEM_LOAD (C++, non-volatile)
- [x] FADD chain per group: acc += res_fp32 (8 FADD)
- [x] Per-group asm volatile: F2FP → HADD2 → STS (4-deep serial chain per group)
- [x] Compiles: 113 regs (vs 186 baseline = 39% reduction!)
- **SASS: ptxas STILL merges all compute across all 4 groups, then emits 4 STS clustered.**
- Same behavior as BF16 and CPP_EPILOGUE. Definitively confirms:
  **ptxas will NEVER interleave STS with compute from source-level inline asm.**

### 1d: @!PT LDS pipeline drain fences — FAILED
- [x] Attempt 1: `@__drain_p ld.shared.b32` with always-false predicate → ptxas DCE
- [x] Attempt 2: real `ld.shared.b32` with unused output (asm volatile) → ptxas DCE
- [x] Attempt 3: real `ld.shared.b32` chain + fence.proxy.async in SAME asm block → ptxas DCE
- All 3 survive in PTX (32 occurrences) but ptxas kills them during SASS assembly.
- **The @!PT LDS fences in CUTLASS are COMPILER-GENERATED by ptxas for CuTe patterns, not from source PTX.**

### Register pressure win (maybe useful)
- 113 regs vs 186 baseline = 33% vs 54.5% RF occupancy
- Untested on B200 — lower RF might reduce persistent-kernel contention

## Phase 2: Manual BF16 conversion (PRMT) — SKIPPED

No point trying. Phase 1 proved ptxas batches STS regardless of compute chain depth.

## Phase 3a/3b: CuTe store pattern — DONE, FAILED

CuTe's `copy(tiled_r2s, ...)` generates `st.shared.v4.b32` via C++ pointer assignment
(`*(uint4*)(smem + offset) = val`), not inline asm. Tested via `-DCUTE_STORE` flag.

**Result**: `st.shared.v4.b32` in PTX (64 stores), byte-identical SASS to baseline.
All 64 STS.128 at identical offsets. ptxas scheduling is NOT affected by whether
the store came from C++ pointer assignment or `asm volatile`.

Two sub-experiments:
1. **cvta.shared approach**: Generic pointer via `cvta.shared.u64` → ptxas **DCE'd all 64 stores**.
   Generic stores through converted pointers are invisible to ptxas as shared memory ops.
2. **smem C++ pointer**: `*(uint4*)(smem + offset)` (extern __shared__ provenance) → generates
   `st.shared.v4.b32 [%r+164864]` in PTX. Compiles to byte-identical STS.128 SASS as baseline.

**Conclusion**: The store mechanism is irrelevant. CuTe's C++ stores and our inline asm stores
produce identical SASS. The CUTLASS STS interleaving comes from loop structure + compute volume,
not from how the `st.shared` PTX was generated.
