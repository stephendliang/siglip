FC2 ncu Diagnosis Guide
=======================

Three questions to answer:
  Q1: Why is fc2_w3 stuck at 1.477ms fused (vs 1.089ms strip = 388us epilogue overhead)?
  Q2: Why does fc2-hybrid Phase 1 (pure CUTLASS) achieve 1.222ms with only 72us overhead?
  Q3: Why do Phase 3b/4 (our dispatch + CUTLASS mainloop) give 2.77ms (2.3x slower)?

All binaries to build BEFORE profiling (compile is fast, ncu is slow):

  make fc2-w3                                          # our kernel, fused
  make fc2-w3 DFLAGS=-DSTRIP_EPILOGUE                 # our kernel, strip (rename binary after!)
  make fc2-hybrid                                      # Phase 1 / 3a (pure CUTLASS)
  make fc2-hybrid-strip                                # Phase 1 strip
  make fc2-hybrid-phase4                               # Phase 4 (broken, 2.77ms)
  make fc2-hybrid-phase4 DFLAGS=-DSTRIP_EPILOGUE       # Phase 4 strip (also broken, 2.63ms)
  make fc2-cutlass                                     # CUTLASS reference
  make fc2-cutlass-strip                               # CUTLASS strip

IMPORTANT: fc2-w3 strip overwrites the same binary. Copy it after build:
  make fc2-w3 DFLAGS=-DSTRIP_EPILOGUE && cp fc2-w3 fc2-w3-strip

Similarly for phase4 strip:
  make fc2-hybrid-phase4 DFLAGS=-DSTRIP_EPILOGUE && cp fc2-hybrid-phase4 fc2-hybrid-phase4-strip

SECTION 3: What to look for — Q1 (fc2_w3 epilogue overhead)
=============================================================================

Compare: ncu_w3_strip vs ncu_w3_fused

The strip kernel runs at 1.089ms. The fused kernel runs at 1.477ms.
The ONLY difference is whether epilogue warps (W2=EpilogueLoad, W3-W6=Epilogue)
execute real work. We already know it's 388us overhead, linear at ~97us/warp.
But WHY.

NOTE: fc2_w3 ALREADY has a dedicated W2 EpilogueLoad warp that TMA-loads
residual into SMEM. Epilogue warps W3-W6 LDS from SMEM (NOT LDG from global).
This matches CUTLASS's architecture. The gap is NOT LDG vs LDS — both use LDS.

CRITICAL CONTEXT: Strip decomposition (30 experiments) proved that NO SINGLE
epilogue operation causes the overhead. TMA-load-only, TMA-store-only, and
compute-only ALL produce the same ~388us overhead. Dispatch pressure, TMEM
timing, and register file occupancy were also individually ruled out. The
overhead is aggregate resource contention from epilogue warps being active.

The question is not "which instruction is slow?" but "which shared hardware
resource is contended when epilogue warps execute?"

Key metrics to compare:

  smsp__warps_issue_stalled_long_scoreboard
    Likely increases fused vs strip. This reflects memory subsystem
    back-pressure from epilogue activity (W2 TMA loads for residual,
    W3-W6 TMA stores for output) saturating DRAM/L2 across 74 clusters.
    Strip decomposition showed compute-only (zero TMA) causes identical
    overhead, so this is one factor among several, not THE bottleneck.

  smsp__warps_issue_stalled_mio_throttle
    If this increases: TMA units or MIO queues are saturated. Epilogue warps
    issuing TMA stores + TMA loads compete with W0's TMA loads for A/B tiles.

  smsp__warps_eligible.avg.per_cycle_active  [NEW]
    The key scheduler metric. Shows how many warps CAN issue per cycle.
    If fused has much LOWER eligibility than strip despite more active warps:
    epilogue warps are stealing issue slots from the MMA warp (W1). This
    directly measures whether epilogue activity slows the K-loop.

  launch__registers_per_thread  [NEW]
    Strip builds at 78 regs, fused at 186 regs. This is the strongest
    correlation with the overhead (54.5% vs 22.9% RF occupancy). However,
    REG_PAD test (186 regs allocated, epilogue skipped) showed strip speed,
    so register allocation alone is NOT the cause — it's register allocation
    PLUS active execution.

  sm__pipe_shared_cycles_active
    If this increases: SMEM port contention. Our STS are clustered 4-8
    back-to-back (measured from SASS), creating burst SMEM write pressure.
    CUTLASS interleaves 6-12 compute ops between each STS.

  l1tex__data_pipe_lsu_wavefronts_mem_shared_op_st.sum  [NEW]
    Actual SMEM store wavefront count. Strip should have near-zero (no STS).
    Fused will show the epilogue's STS.128 traffic. Combined with
    sm__pipe_shared_cycles_active, tells you if SMEM stores are the
    contention source.

  l1tex__data_pipe_lsu_wavefronts_mem_shared_op_ld.sum  [NEW]
    SMEM load wavefronts. Both strip and fused have K-loop LDS activity
    from MMA. If fused adds significantly more: epilogue LDS activity is
    competing with K-loop LDS.

  l1tex__data_pipe_lsu_wavefronts_mem_global_op_ld.sum  [NEW]
    Global load wavefronts. fc2_w3 does NOT use LDG in the epilogue — W2
    loads residual via TMA (not counted here). This metric should be similar
    between strip and fused. If fused is much higher: something unexpected
    is issuing global loads (debug).

  dram__bytes_read.sum
    Should increase by roughly the residual matrix size (W2's TMA loads):
    928256 * 768 * 2 bytes (bf16) = ~1.36 GB. If it increases by MORE, there's
    wasted/replayed traffic. TMA loads go through DRAM even though they
    target SMEM — they still consume memory bandwidth.

  sm__warps_active.avg.per_cycle_active
    Strip should show ~2-3 active warps (W0+W1 only).
    Fused should show ~6-7. If fused shows less than expected, warps are
    frequently stalled (sleeping/barrier).

  smsp__inst_executed.sum
    Fused should be ~2-3x strip (epilogue adds instructions). If it's way more,
    something is being replayed or looped unexpectedly.

SECTION 4: What to look for — Q2 (fc2_w3 vs CUTLASS fused)
=============================================================================

Compare: ncu_w3_fused vs ncu_hybrid_fused

Both produce correct fused output. fc2_w3=1.477ms, hybrid=1.222ms.
Both have the SAME epilogue architecture: dedicated EpilogueLoad warp
(our W2, CUTLASS W3) pre-loads residual into SMEM via TMA; epilogue warps
LDS from SMEM. Both use 4 epilogue warps. Both use ReuseSmemC (same staging
SMEM for load and store). The difference is 7 vs 8 warps and the three
SASS-verified structural differences below.

KNOWN STRUCTURAL DIFFERENCES (SASS-verified, see fc2_w3_vs_cutlass_sass.md):

  1. STS scheduling: our BF16 compute chain (F2FP → HFMA2 → HADD2 = 3 deep,
     all groups independent) is too short to shadow STS. Result: 4-8 STS fire
     back-to-back with 0-2 ops between them. CUTLASS's FP32 chain (FFMA × 64
     per sub-iter = long compute stream) provides 6-12 compute ops between each
     STS. Same total STS count (32/tile), dramatically different temporal spread.

  2. @!PT LDS pipeline drain fences: CUTLASS inserts 4 dummy LDS loads per
     sub-iter (never-true predicate, RZ destination) after STS block, before
     MEMBAR + FENCE. These drain the LSU pipeline ensuring STS are visible in
     SMEM before TMA store reads it. We have NONE.

  3. BAR.SYNC.DEFER_BLOCKING: NOT a difference. We ALREADY have 2 per sub-iter
     (pre-store bar.sync at line 1097, post-store bar.sync in EPI_WAIT at line
     578). ptxas auto-upgrades to DEFER_BLOCKING on SM100a. Removing both
     (NO_PRE_STORE_BAR + NO_POST_STORE_BAR, 17→1 barriers) = zero perf effect.
     Barriers are identical between us and CUTLASS.

Key metrics:

  smsp__warps_issue_stalled_long_scoreboard
    Both kernels use TMA for residual loads (not LDG). Long scoreboard
    reflects DRAM/L2 back-pressure from W2/W3's TMA residual loads and
    W0's TMA A/B loads competing for memory bandwidth. If w3 is much
    higher: our epilogue's TMA load/store pattern creates more memory
    pressure than CUTLASS's.

  sm__pipe_shared_cycles_active
    Both kernels have similar SMEM activity (LDS from staged residual +
    STS for output). If w3 is higher: our clustered STS pattern creates
    more SMEM port contention. If CUTLASS is higher: CUTLASS's extra
    @!PT LDS fences add SMEM traffic but the interleaved STS pattern
    makes it cheaper overall.

  l1tex__data_pipe_lsu_wavefronts_mem_shared_op_st.sum  [NEW]
    SMEM store wavefronts. Both do 32 STS.128 per tile, so total should be
    similar. But the TEMPORAL distribution differs (our: burst, CUTLASS:
    spread). This metric alone won't show the burst pattern, but combined
    with sm__pipe_shared_cycles_active shows total SMEM store pressure.

  l1tex__data_pipe_lsu_wavefronts_mem_shared_op_ld.sum  [NEW]
    SMEM load wavefronts. Both should be similar (both LDS residual + bias
    from SMEM). CUTLASS might be slightly higher due to @!PT LDS fences
    (4 dummy LDS per sub-iter that don't actually load data but generate
    wavefronts). Large difference = unexpected architecture mismatch.

  l1tex__data_pipe_lsu_wavefronts_mem_global_op_ld.sum  [NEW]
    Global load wavefronts. NEITHER kernel does LDG in the epilogue —
    both use TMA for residual. These should be similar. Large difference
    = unexpected code path difference.

  smsp__warps_eligible.avg.per_cycle_active  [NEW]
    Scheduler pressure. If w3 has lower eligibility: our epilogue warps are
    creating more stalls that reduce the MMA warp's issue opportunities.
    CUTLASS's interleaved STS pattern should produce fewer burst stalls,
    leaving more issue slots for MMA.

  launch__registers_per_thread  [NEW]
    Our fused: 186 regs. CUTLASS: ~253 regs. Higher reg count in CUTLASS
    means lower occupancy but CUTLASS is still faster — confirms the gap
    is not from occupancy differences but from epilogue scheduling.

  smsp__warps_issue_stalled_not_selected
    Higher in hybrid (8 warps) is expected — more warps competing for issue
    slots. But if w3 has high not_selected too, the scheduler is struggling.

  dram__throughput.avg.pct_of_peak_sustained_elapsed
    Both should be similar (same data volume — both TMA-load residual).
    If w3 is higher: our TMA load/store pattern is less efficient.

  lts__t_sectors_op_read.sum
    L2 read sectors. Both use TMA for residual, so L2 behavior should be
    similar. Large differences indicate different TMA descriptor configs
    or caching behavior.

SECTION 5: What to look for — Q3 (Phase 4 broken at 2.77ms)
=============================================================================

Compare: ncu_hybrid_fused (1.222ms) vs ncu_phase4_fused (2.77ms)

CRITICAL: both use CUTLASS's collective_mainloop and collective_epilogue.
Both use 8 warps. Both use the same SMEM layout, same pipelines.
The ONLY difference is tile scheduling: CUTLASS uses CLC scheduler with
fetch_next_work() inside a do/while loop. Phase 4 uses a static for-loop
with pre-computed tile range.

Also compare strips: ncu_hybrid_strip vs ncu_phase4_strip
Phase 4 strip is ALSO broken (2.63ms vs 1.15ms), so the problem is in
the mainloop dispatch, not the epilogue.

Key metrics:

  smsp__warps_issue_stalled_barrier
    If Phase 4 is WAY higher: warps are stuck at mbarrier waits. This means
    pipeline producer/consumer handshakes are broken — load warp isn't feeding
    data fast enough, or pipeline init is wrong so barriers start in wrong state.

  smsp__warps_issue_stalled_wait
    If Phase 4 is WAY higher: warps are stuck at cp.async/TMA wait groups.
    Pipeline stages might not be advancing correctly.

  smsp__warps_issue_stalled_sleeping
    If Phase 4 is WAY higher: warps are calling nanosleep or similar idle
    patterns. Could be CUTLASS's trylock/backoff in CLC replacement.

  smsp__cycles_active.avg
    Should be ~2.3x higher in Phase 4 (since it takes 2.3x longer).
    If it's LESS than 2.3x, some cycles have NO warps active at all = deadlock
    or serialization at tile boundaries.

  sm__warps_active.avg.per_cycle_active
    Phase 1 should show ~3-4 active warps sustained.
    Phase 4: if much lower, warps are serialized. If similar, warps are active
    but doing useless work (spinning on barriers, TMA retries).

  smsp__inst_executed.sum
    Phase 4 should ideally have similar instruction count to Phase 1 (same work).
    If Phase 4 has MORE instructions: the static loop is executing extra
    iterations, or CUTLASS's internal trylock/retry paths are spinning.
    If Phase 4 has FEWER instructions but takes longer: pure stall time.

  Also specifically check:
    smsp__warps_issue_stalled_long_scoreboard
    smsp__warps_issue_stalled_mio_throttle
    These would indicate TMA or memory subsystem problems in the mainloop.

SECTION 9: Specific hypotheses to test
=============================================================================

HYPOTHESIS A: Phase 4's static tile loop doesn't initialize CLC state correctly.
  CUTLASS's do/while calls scheduler.fetch_next_work() which internally does
  CLCX/CLC barrier operations. Phase 4 skips CLC entirely but still initializes
  CLCPipeline. Maybe the CLC pipeline init puts hardware in a bad state when
  CLC isn't actually used.
  TEST: Compare Phase 4's barrier stall metric vs Phase 1.
  If barrier stalls dominate Phase 4: CLC init is the problem.

HYPOTHESIS B: ALREADY RULED OUT — tile overlap serialization.
  Phase 4 strip is 2.63ms (vs Phase 1 strip 1.15ms). Since strip has no
  epilogue, the problem is in the mainloop dispatch itself, not epilogue
  overlap. Do not investigate further.

HYPOTHESIS C: CUTLASS's mainloop.load()/mma() do internal CLC queries.
  Even though we pass static tile coords, the collective functions might
  internally call CLC operations that fail or spin without proper CLC setup.
  TEST: Look at smsp__inst_executed.sum for Phase 4 vs Phase 1.
  If Phase 4 has 10x+ more instructions: internal spin loops.
  Also check smsp__warps_issue_stalled_sleeping: CLC backoff uses nanosleep.

HYPOTHESIS D: Pipeline phase/state mismatch.
  CUTLASS's operator() calls pipelines in a specific order with specific
  initial states. Phase 4 might initialize pipelines but then call
  mainloop.load()/mma() which expect different initial pipeline state.
  TEST: If barrier stalls are high AND concentrated in the first few tiles,
  it's an init problem. If stalls are uniform across all tiles, it's a
  per-tile handshake problem.

HYPOTHESIS E: Two-CTA cluster coordination broken.
  cta_group::2 requires both CTAs in a cluster to coordinate via multicast
  mbarriers. Phase 4's static scheduling might assign tile ranges that
  don't align between the two CTAs.
  TEST: Run Phase 4 with a single CTA cluster (if possible). Or check if
  only odd/even CTAs are stalling.

SECTION 10: Priority order
=============================================================================

Do this in order. Stop as soon as root cause is clear.

  1. Build all binaries, confirm wall times (5 min)
  2. Run targeted metrics (Section 2) on all 6 binaries (~12 min)
  3. Export CSVs, run ncu_diff.py on the 3 comparison pairs
  4. Read the diffs. The top divergent metrics should point at the cause.
  5. If Q3 (Phase 4) shows barrier or sleeping stalls >> Phase 1:
     -> CLC init / pipeline state is the problem
     -> Next step: read CUTLASS operator() to find what CLC does at runtime
  6. If Q3 shows similar stall profile but more instructions:
     -> Internal spin loops in collective_mainloop
     -> Next step: grep CUTLASS source for nanosleep/trylock in load()/mma()
  7. If Q1 shows long_scoreboard dominates fused vs strip:
     -> W2's TMA residual loads + epilogue TMA stores saturate DRAM/L2
     -> ncu numbers quantify how much memory bandwidth epilogue consumes
  8. Only run --set full if targeted metrics are inconclusive

SECTION 11: RESULTS (B200-verified 2026-04-05)
=============================================================================

Data: data/ncu_20260405_202913/
Analysis: python3 tools/ncu_anova.py

Q1 ANSWERED: Epilogue overhead is from STS clustering causing barrier stalls.
  - short_scoreboard: +137K (+11261%) from back-to-back STS WAR hazards
  - barrier: +71K (+31%) from uneven warp progress
  - long_scoreboard: +0.3% = DRAM is NOT the bottleneck
  - mio_throttle: +0.3% = TMA is NOT the bottleneck

Q2 ANSWERED: Head-to-head, barrier stalls are the dominant difference.
  - barrier: w3=298K vs cutlass=31K (+860%, accounts for 110% of stall delta)
  - short_scoreboard: basically identical in fused mode (139K vs 136K)
  - Barriers are a SYMPTOM of STS clustering, not the cause
    (removing barriers = zero effect, proven by NO_PRE_STORE_BAR experiment)
  - CUTLASS's epilogue DECREASES barrier stalls by 60K (fills idle time)
  - Our epilogue INCREASES barrier stalls by 71K (STS bursts → uneven progress)

Q3 ANSWERED: Phase 4 does ~2x the work of CUTLASS.
  - inst_executed: 396M vs 163M (+143%)
  - cycles_active: 4.9M vs 1.9M (+152%)
  - long_scoreboard: 6.87M vs 2.74M (+151%)
  - Static tile dispatch is fundamentally broken (redundant work or L2 thrashing)

RULED OUT by data:
  - DRAM bandwidth: long_scoreboard flat (+0.3%)
  - TMA saturation: mio_throttle flat (16 → 16)
  - Warp scheduler: not_selected small absolute (5.8K)

CONFIRMED:
  - STS clustering is the root cause of epilogue overhead
  - Mechanism: back-to-back STS → SMEM port contention → uneven warp progress
    → barrier stall inflation (+860%)
  - Cannot be fixed from source (ptxas controls STS scheduling, 6+ approaches tried)
